# Ревью Rust-версии

Три независимые проверки кода от 2026-09-26: ревью Rust (корректность, гонки, лимиты Telegram),
ревью безопасности (утечка токена, HTML-инъекции, права, секреты в истории git) и построчная
сверка поведения с Python-версией. Каждую находку я перепроверил по коду. Если находка
подтверждалась, сначала появлялся падающий тест, потом исправление.

## Исправлено

| Находка | Уровень у ревьюера → после проверки | Исправление | Тест |
|---|---|---|---|
| Текст, начинающийся с `/` (например `/r/foo`), считался командой и молча пропадал. В Python такой текст в шаге «жду контент» становился предложением | — → средний | Командами считаются только `/start` и `/stats` | `user_flow::slash_text_that_is_not_a_known_command_is_content` |
| При остановке сервиса воркер публикаций прерывался посреди отправки. Запись оставалась в `publishing`, и после обычного рестарта приходила ложная тревога «проверьте канал» | средний → средний | Блокировка `App::sending` удерживается от захвата публикации до записи результата. При остановке бот берёт её (до 30 с), и только потом останавливает воркер | `publication::shutdown_waits_for_a_send_in_progress_and_blocks_new_claims` |
| Если за 30 с не удавалось дождаться завершения обработки, ранний `?` пропускал остановку воркера и закрытие БД | средний → низкий | Остановка и очистка вынесены так, что выполняются при любом исходе | покрыто структурой `serve`/`dispatch` |

| `/stats` логировал ошибку без `App::redact` | **критический** → низкий | `redact` добавлен для единообразия | `stats::network_errors_are_logged_without_the_token` |
| Функции длиннее 50 строк: `Config::parse`, `import::run`, `serve`, `user::submit`, `admin::decide` | качество | Разбиты на части без изменения поведения | все тесты до и после |

Почему «критический» оказался низким. Ревьюер предположил, что ошибка reqwest с URL и токеном
попадёт в журнал. Но teloxide-core сам вызывает `without_url()` для сетевых ошибок
(`errors.rs:818`). Тест с недоступным API это подтвердил: в журнале
`error sending request … os error 10061`, токена нет. `redact` остаётся второй линией защиты.

## Найдено до ревью, во время TDD

- teloxide `html_text()` / `html_caption()` возвращает текст **без экранирования**, если в
  сообщении нет entities, и `None` для подписи без entities. Без своей обёртки
  (`text::to_html`) пользовательский `<` снова ломал бы карточку (ошибка F2 из Python).
  Тест: `user_flow::full_text_submission_reaches_moderators_with_escaped_html`.
- Фикстуры callback-сообщений с `date: 0` Bot API считает недоступными
  (`InaccessibleMessage`). Настоящие callback'и так не выглядят, это была ошибка в тестах.

## Проверено, замечаний нет

- **Публикация не более одного раза.** `claim_due` захватывает запись одним
  `UPDATE … RETURNING`, `decide` меняет только `pending`, восстановление никогда не отправляет
  `publishing` повторно.
- **SQLite.** Один коннект плюс `BEGIN IMMEDIATE` не дают взаимоблокировок: пул асинхронный, и
  нет пути, где держатель транзакции снова берёт пул.
- **`Notify`.** `notify_one` сохраняет разрешение, если воркер ещё не ждёт, так что пробуждение
  не теряется. Коммит решения происходит раньше уведомления.
- **Лимиты Telegram.** Подпись 1024 и текст 4096 считаются в UTF-16, как в Telegram.
  `callback_data` не длиннее 51 байта при лимите 64.
- **Права.** Все `adm_*` и `stats:` сначала проверяют `ADMIN_IDS`. Подача работает только в
  личке.
- **HTML.** Текст и подписи пользователя проходят через `to_html`. Имя в «Автор:» и текст
  ошибки экранируются. Username в Telegram содержит только `[A-Za-z0-9_]`.
- **SQL.** Везде параметры sqlx, склейки строк нет.
- **Секреты.** В полной истории git нет токенов, IP-адресов и паролей. Внутренние заметки не
  отслеживаются.
- **systemd.** Отдельный пользователь, `bot.env` 0600, `ProtectSystem=strict`,
  `NoNewPrivileges`, пустой `CapabilityBoundingSet`, лимиты памяти, CPU и задач.
- **Паритет.** `messages.json` побайтно совпадает с Python-версией. Жёстко заданные строки,
  раскладки клавиатур, alert и toast, формулы и формат статистики совпадают. Отличия описаны в
  [PARITY.md](PARITY.md).

## Оставшиеся замечания (не исправлялись)

- `cargo audit`: уязвимостей нет. Есть предупреждение RUSTSEC-2026-0173: `proc-macro-error2`
  не поддерживается. Крейт приходит через teloxide, это не уязвимость.
- Пользователь может открыть несколько альбомов в пределах 1,5 с. Память ограничена скоростью
  отправки одного пользователя, записи живут секунды.
- `MessageId(id as i32)` при чтении из БД: значения записываются только из настоящих
  `MessageId` или проходят проверку диапазона при импорте.

## Границы заключения

Проверки — это чтение кода и тесты против имитации Bot API (wiremock). Живой Telegram, сеть и
поведение Bot API (например, что `copyMessage` игнорирует `caption` у текстового сообщения, F1)
проверяются отдельно, на тестовом боте.
