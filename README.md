# tg-bot-predlozhka-rust-version

Telegram-бот «предложка». Пользователи присылают контент для канала, администраторы
модерируют его в общем чате, одобренное публикуется в канал с задержкой.

Это переписанная на Rust версия Python-бота
[Betreazen/tg-bot-predlozhka](https://github.com/Betreazen/tg-bot-predlozhka)
(aiogram + PostgreSQL + Redis). Вместо трёх контейнеров здесь один процесс с
SQLite: teloxide, sqlx, tokio. Тексты, кнопки, лимиты и задержки остались прежними.
Данные Python-версии переносятся подкомандой `--import`.

## Возможности

- Подача в личке: текст, фото, видео, документы (в том числе GIF), аудио и альбомы
  целиком. Подтверждение и выбор авторства.
- Лимит — 2 предложения в сутки по часовому поясу (Europe/Moscow). Лимит проверяется в
  той же транзакции, что и запись, поэтому двойное нажатие его не обходит.
- Карточка модерации в админ-чате: «Принять и опубликовать» (с подтверждением),
  «Принять», «Отклонить», блокировка и разблокировка автора. После решения к карточке
  дописывается подвал: кто решил и когда.
- Уведомления автору о решении и о блокировке.
- Публикация в канал через заданное время: подпись «Автор:», подвал и хэштеги.
  Альбомы публикуются альбомом.
- Отложенные публикации хранятся в БД и переживают рестарт. Каждая публикация
  уходит не более одного раза: если процесс упал посреди отправки, бот не повторяет её,
  а просит администраторов проверить канал.
- Неудачная публикация повторяется (по умолчанию 2 попытки с паузой 30 с). Затем
  приходит сообщение в чат ошибок.
- `/stats` для администраторов: статистика по месяцам с листанием.

Что изменилось относительно Python-версии и почему, описано в [docs/PARITY.md](docs/PARITY.md).

## Потребление ресурсов

Python-стек на том же сервере в простое (cgroup v2, 2026-09-25):

| Контейнер | Память | Средний CPU |
|---|---|---|
| бот (Python) | 65 MiB, пик 244 | 1.48 % ядра |
| PostgreSQL | 16 MiB, пик 28 | 0.45 % |
| Redis | 4 MiB, пик 18 | 0.91 % |
| **Итого** | **~85 MiB** | **~2.84 % ядра** |

Почти весь CPU Python-бота уходил не на работу бота. Сам процесс за 11,5 суток
потратил 125 CPU-секунд. Всё остальное съедал Docker `HEALTHCHECK`: каждые 30 секунд он
запускал новый интерпретатор Python, тот импортировал SQLAlchemy и открывал соединения
с базой, и так 0,42 CPU-секунды за каждый прогон. Rust-версия обходится без
периодических проверок. За живостью следит systemd, а фоновый планировщик публикаций
при пустой очереди просто ждёт события и не просыпается по таймеру.

Цифры Rust-версии появятся в [docs/BENCHMARK.md](docs/BENCHMARK.md) после суток работы
на том же сервере.

## Запуск: бинарник + systemd (рекомендуется)

```bash
# на машине сборки
docker build --target build -t tg-bot-predlozhka:build .
id=$(docker create tg-bot-predlozhka:build) && docker cp "$id":/usr/local/bin/bot ./bot && docker rm "$id"

# на сервере (root), рядом с bot, messages.json, .env.example и deploy/
bash deploy/install.sh .
nano /etc/tg-bot-predlozhka/bot.env        # токен, чаты, ADMIN_IDS
systemctl enable --now tg-bot-predlozhka
journalctl -u tg-bot-predlozhka -f
```

Пошагово, с проверкой, обновлением, резервной копией и переходом с Python — в
[docs/DEPLOY.md](docs/DEPLOY.md).

Бот должен быть администратором канала с правом публикации и участником админ-чата
и чата ошибок. **Не запускайте два процесса с одним токеном**: Telegram отвечает
второму опросчику ошибкой 409.

## Docker

```bash
docker build -t tg-bot-predlozhka .
docker run -d --name predlozhka --restart unless-stopped --env-file .env \
  -v "$PWD/data:/app/data" tg-bot-predlozhka
```

Образ distroless, процесс работает не от root (UID 65532), каталог `data` должен
быть доступен этому UID на запись. `HEALTHCHECK` в образе нет намеренно, причина
описана выше.

## Настройки

Бот читает только переменные окружения. `.env` подгружает systemd (`EnvironmentFile`)
или Docker (`--env-file`). Пример лежит в [.env.example](.env.example). Значения
обрезаются от пробелов и `\r` (файл, сохранённый в Windows), кавычки снимаются.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| BOT_TOKEN | обязательно | Токен от @BotFather |
| CHANNEL_ID | обязательно | Канал для публикаций |
| ADMIN_CHAT_ID | обязательно | Чат модерации |
| ERROR_CHAT_ID | = ADMIN_CHAT_ID | Сообщения о неудачных публикациях |
| ADMIN_IDS | пусто | ID модераторов через запятую или точку с запятой |
| DATA_DIR | data | Каталог с `bot.db`, локальный диск |
| MESSAGES_PATH | messages.json | Тексты (формат Python-версии) |
| SUBMISSIONS_PER_DAY | 2 | Лимит подач в сутки |
| TIMEZONE | Europe/Moscow | Границы суток для лимита и месяцев для `/stats` |
| PUBLICATION_DELAY_MINUTES | 2 | Задержка публикации после одобрения |
| MAX_FILE_SIZE_MB | 200 | Максимальный размер файла |
| FOOTER_TEXT | пусто | Строка под постом (HTML), пусто — нет |
| HASHTAGS | пусто | Хэштеги под постом, например `#a #b` |
| REQUIRE_CONFIRMATION | true | Шаг «Подтвердить» перед вопросом об авторстве |
| ENABLE_BLOCKING | true | Учитывать блокировку пользователей |
| MAX_RETRY_ATTEMPTS | 2 | Попыток публикации |
| RETRY_DELAY_SECONDS | 30 | Пауза между попытками |
| RUST_LOG | info | Уровень журналов |

Если меняете лимиты, поправьте и тексты в `messages.json`: там упоминаются
«2 предложения» и «200 МБ».

## Команды бинарника

| Команда | Что делает |
|---|---|
| `bot` | Запуск |
| `bot --check` | Проверяет настройки и тексты, создаёт или обновляет схему БД. К Telegram не обращается |
| `bot --import <dir>` | Импорт выгрузки Python-версии в пустую БД (см. [OPERATIONS.md](docs/OPERATIONS.md)) |
| `bot --version` | Версия |

Бот держит блокировку `DATA_DIR/.instance.lock`, поэтому второй процесс на тех же данных
не запустится.

## Разработка

```bash
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Тесты не ходят в Telegram: Bot API имитирует локальный wiremock, база создаётся во
временном каталоге, настоящий токен не нужен.
